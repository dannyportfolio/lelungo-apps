## How to use this roadmap

The recommended Phase 0-12 framework is retained, with one repository-driven correction: **Phase 1 starts with authoritative authentication, same-tenant membership authorization, and PostgreSQL isolation evidence; it does not start with Property.** Property begins in Phase 2 only after that security boundary passes.

Phases are delivery horizons, not permission for a broad batch. A phase may contain several independently approved OpenSpec changes. Each change must preserve the modular-monolith dependency direction, make current/target status explicit, use additive migrations, update architecture and session handoff, record actual checks, and stop at its acceptance boundary. A readiness verdict allows planning/applying the next narrow slice; it does not assert production readiness or automatically start the next phase.

Cross-cutting rules for every phase:

- external input is validated, identity is verified, tenant is resolved from trusted server context, permission/resource scope is authorized, then an application service owns the operation;
- tenant-owned persistence has explicit tenant keys, ownership constraints/indexes, minimum-field access, cross-tenant negative tests, and no client-selected authority;
- correctness-sensitive decisions use authoritative PostgreSQL constraints/transactions, not UI, search, cache, or an eventually consistent projection;
- public/provider contracts use explicit DTOs, idempotency where retries can duplicate intent, redacted telemetry, and append-oriented audit/outbox capture where required;
- no phase edits an applied migration, runs a production migration automatically, deletes legacy data/code in the replacement release, or claims an unavailable check passed;
- a separately accepted ADR/OpenSpec change is required before broker, gRPC, dedicated search, microservice, or other distributed infrastructure adoption.

## Phase transition checklist

Before any phase/slice is marked complete or the next begins:

1. Scope/non-goals and repository evidence are current; any contradiction updates the OpenSpec design rather than being silently worked around.
2. Authentication, authorization, tenant/property ownership, validation, privacy/DTO exposure, audit, concurrency/idempotency, migrations, dependencies, infrastructure, and external side effects were reviewed where applicable.
3. Relevant unit, disposable-PostgreSQL integration, concurrency, contract, E2E, migration, security, performance, recovery, and rollback checks ran; exact results and blockers are recorded.
4. Documentation and `docs/runbooks/session-handoff.md` describe implemented behavior only, list debt/open decisions, and name the recommended next narrow slice.
5. Application, schema, worker/provider, and data rollback is safe for existing records; production migration/deployment remains an explicitly authorized operation.
6. A readiness report says `READY FOR PHASE <n+1>` or `NOT READY FOR PHASE <n+1>` with supporting evidence. The next phase does not start automatically.
